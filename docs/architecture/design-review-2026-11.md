# Design Review — Technology Architecture (2026-11)

Adversarial review of two proposals:

- **Original:** TS monorepo, React + Vite, Node + Fastify, PostgreSQL, combat engine shared as a TS package, JSON/YAML
  content validated with Zod.
- **Counter-proposal:** keep TS full-stack; add PixiJS for 2D scenes; Capacitor for later iOS/Android; separate API and
  idle-simulation workers; combat engine as pure deterministic functions with injectable RNG; JSON as canonical content
  format; pnpm workspaces and possibly Drizzle; server as sole authority over combat, inventory and rewards.

**Verdict:** TypeScript full-stack stays (confidence ~80%). Most of the counter-proposal is adopted, with four
corrections. The biggest gap in *both* proposals was that neither defined the **execution model** of the combat engine
nor of idle expeditions — the decisions most likely to force a rewrite after six months.

## 1. PixiJS vs Phaser vs Godot

- The real underestimated cost is **art, not the engine**. A retina full-screen illustration (2732×2048 RGBA) is ~22 MB
  of GPU memory; three resident at once can get an iOS Safari tab killed. A texture budget, one resident scene and
  compressed textures (KTX2/Basis) are required from day one.
- Skeletal animation (Spine) needs a license; DragonBones is abandoned. For the POC, static sprites + tweens (idle bob,
  lunge, hit flash, shake) deliver most of the feel without an animation pipeline.
- Phaser brings scenes, tweens, particles, cameras and a loader, but its scene system competes with React state.
  PixiJS is renderer-only: more assembly, cleaner integration as one component.
- Godot: web export is tens of MB, has known iOS Safari issues, no C# on web in Godot 4, and splits the codebase
  (GDScript client vs TS server) — losing shared content schemas and much AI-assisted productivity. It wins for a final
  native client, not for a web-first POC.
- **Decision:** UI in DOM/React; scene in a canvas behind a `SceneRenderer` interface. PixiJS vs Phaser decided by
  spike. The serious mistake would be building inventory, forms and text inside a canvas.

## 2. Capacitor

- Fits well **because idle runs on the server**: no background execution needed, which is what WebViews do worst.
- Real risks: WKWebView memory limit (silent process kill), WebGL context loss on background, audio unlock rules, no
  reliable service workers on iOS (no PWA-dependent offline), weak GPUs on low-end Android.
- Notifications: schedule a local notification for `endsAt` when an expedition starts; party events and early deaths
  arrive via server push.
- IAP: native IAP (e.g. RevenueCat); external payment rules vary by region and change.
- The real hedge if Capacitor fails is a **clean client/server protocol** so only the client is replaced. Capacitor is
  out of the POC except for a spike.

## 3. Shared combat engine?

- Share **contracts, not the implementation**. With 0.5–1 s ticks, 100 ms latency is imperceptible; the client renders
  server events and needs no prediction.
- Shared: content schemas, types, protocol, display-only stat derivation. Not shared: the simulation.
- The engine's real second consumers are the balance CLI and content tools, which run in Node. Shipping it to the client
  creates version skew without security benefit (formulas will be datamined anyway; authority is what protects us).
- **Critical:** the engine must be `step(state, inputs, rng) → (state, events)`. Live injects manual inputs at tick
  boundaries; idle is the same loop with inputs generated by automation rules. A batch "simulate whole fight" design
  breaks live; a real-time room design breaks idle. **Risk #1.**

## 4. Determinism

Realistic because the simulation runs only in Node with a pinned version, under these rules:

- Integer arithmetic (HP/damage integers, percentages in basis points).
- No `Math.sin/exp/pow/log` in the simulation (implementation-approximated per ECMAScript; may differ across engines
  and versions). Use lookup tables if needed.
- Seeded PRNG (e.g. PCG32) with **separate named streams** (combat, loot, encounters) so adding a loot roll does not
  change combat outcomes.
- Explicit intra-tick event ordering (initiative, then actor ID).
- No clock access — time is an input.
- `engineVersion` + `contentHash` stored with every simulation.
- Golden replays in CI (same seed ⇒ same hash), run on two Node versions.
- "Pure" means pure at the boundary; internally the step mutates a working copy (immutable copies every tick would
  create GC pressure in Monte Carlo).

## 5. Idle at scale

- **Precompute at start, reveal progressively.** In one transaction: lock character, escrow consumables, snapshot
  stats, simulate the *whole* expedition, store the timeline with `seed`, `engineVersion`, `startsAt`, `endsAt`.
- No live processes; no version problem for in-flight expeditions.
- Wall-clock duration ≠ simulated time: duration defines the number of encounters; each encounter is simulated tick by
  tick. Matches concept §6.1 and makes "faster expeditions" a pacing multiplier.
- The client never receives future events (server only exposes `t ≤ now`).
- Settlement: job at `endsAt` runs `UPDATE … WHERE status='running' RETURNING` and pays in the same transaction;
  worker crashes are retried without double effects.
- Cancellation: cut the timeline at `now` and settle per cancellation policy.
- Party: when a member leaves, re-simulate the remainder from `t` with remaining members using a revision-derived seed.
  Invitations carry `config_version`; starting locks characters in ID order to avoid deadlocks.
- Hidden risk: estimates need Monte Carlo (~200 runs × ~7,000 ticks) — may take seconds. Cache per (build hash, region,
  duration) or use a per-encounter model. Spike 1.
- Separate workers: logical separation yes, separate deployable no (precompute takes tens of ms and can run in-request).

## 6. Live multiplayer

- Fastify + WebSocket is enough for parties of ≤4 at ~1 s ticks.
- The real problem is in-memory state: **instance lease** in Postgres (`instance_id`, `node_id`, `expires_at`),
  **checkpoints** at meaningful boundaries (location change, combat end, loot pickup), restore from last checkpoint on
  node failure.
- Ticks exist only during combat; exploration is command/response.
- Disconnection **does not pause combat**; the character continues on automation. This removes the
  disconnect-to-survive exploit and gives automation a purpose in live.
- Colyseus solves rooms, reconnection and routing — compare against in-house in spike 3 behind an `InstanceHost`
  interface.
- Corpses cannot live in the instance (it dies); they are a persistent per-player entity bound to a location and spawned
  into future instances.

## 7. PostgreSQL only?

- Yes up to ~1,000 CCU: persistence, job queue (`SKIP LOCKED`), advisory locks, `LISTEN/NOTIFY` for cross-node invites.
- Traps: serverless/pooled Postgres and PgBouncer transaction mode don't support `LISTEN`; WebSockets need long-lived
  processes, so the game server cannot be serverless.
- Redis when multiple live nodes need presence/party pub/sub or global rate limiting. Dedicated queue at thousands of
  jobs/s or cross-service integration — not before ~10,000 CCU.

## 8. Economy and security

- `activity_state` (`none | live | expedition`) + `activity_id`, changed only via compare-and-set: makes live+idle
  simultaneously impossible even with two devices.
- Append-only ledger with unique idempotency key `(source_type, source_id, reward_idx)`; `CHECK (qty >= 0)` on stacks;
  equipment as unique rows with UUIDs.
- Single serialization point: `SELECT … FOR UPDATE` on the character row for every mutation.
- Consumables escrowed at start and returned at settlement; in live they go to a **run bag** — the concept's
  "unsecured loot", committed when returning to Sanctuary.
- `command_id` deduplication — without it, reconnect retries duplicate potions.
- While a live instance holds the lease, REST cannot touch the inventory.
- Server clock only.

## 9. Declarative content

JSON + Zod is fine as a format but not as a pipeline. Inevitable tooling:

1. Content compiler: referential integrity, region graph checks (connected, 70% reachable without secrets, mandatory
   boss present), versioned bundle with hash.
2. JSON Schema generated from Zod for editor autocompletion.
3. Scene editor — **Tiled** (image + object layers with properties, JSON export) instead of a custom editor.
4. Balance simulator CLI (TTK, win rate by level, XP/hour live vs idle) — answers concept risk 15.1.
5. Effects as a closed set of parameterized types (e.g. `taunt{charges, unit: "attacks"}`); no expression language in
   JSON.
6. Stable IDs, never renamed.

## 10. Cost and complexity

- **Cut / defer:** Capacitor (spike only), separate worker deployable, Redis, horizontal scaling, Spine, live coop
  (phase 2), complex auth (guest + email is enough).
- **Keep from day 1 (cheap now, expensive later):** `participants[]` in instances and expeditions, idempotent ledger,
  activity lock, injectable server clock (time travel for tests/QA), debug panel.

## Changes vs the original proposal

1. Combat engine becomes server-only; clients share contracts, content and display stats.
2. PixiJS added for the scene/combat viewport.
3. JSON is the single canonical content format (no YAML).
4. Idle precompute, Postgres job queue, ledger and activity lock made explicit.
5. Tiled and the balance simulator added as first-class tools.

## Rejected from the counter-proposal

- Separate worker deployable in the POC (logical separation kept, single process).
- Committing to Capacitor before device testing (kept as hypothesis).
- Purity via immutability per tick (GC cost in Monte Carlo).
- PixiJS for the whole interface (scene only).
- Drizzle accepted, but locks and idempotency stay in explicit SQL.
